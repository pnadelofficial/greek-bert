# Audit: why GreekBERT gains are smaller than expected

Findings ordered by (expected impact) / (cost to fix). Items 1–4 are, in my
judgment, the reason the deltas are small.

---

## TIER 0 — These are not hyperparameters. They cap every downstream result.

### 1. `mlm_masking` silently dropped the 80/10/10 recipe — and the docs claim it's there

`scripts/utils.py::mlm_masking` replaces **100%** of selected tokens with
`[MASK]`. Verified empirically against the current code:

```
selected (labelled) fraction    : 0.2993  (target 0.30)
of selected, replaced by [MASK] : 1.0000  (target 0.80)
of selected, left unchanged     : 0.0000  (target 0.20)
of selected, random token       : 0.0000  (target 0.10)
```

The docstring says "same as BERT/RoBERTa: 80% [MASK] / 10% random / 10%
unchanged". The implementation does 100/0/0. The old numpy version *did*
implement the split (`mask_mask = rand < mask_prob * 0.8`); the "dynamic
masking" rewrite lost it.

Why this matters more here than in a normal BERT: you mask **30%** of tokens and
train **20 epochs**. The model sees a `[MASK]` at ~30% of all positions and
never once has to recover a token that is still visible in the input. Two
consequences:

- **No exposure-bias correction.** Every downstream task (spaCy
  morphologizer/lemmatizer, WSD, the SBERT encoder) reads **unmasked** text. The
  encoder's entire training distribution says "a third of what I'm looking at is
  `[MASK]`". At inference the `[MASK]`s are gone and the residual stream statistics
  shift. That is a direct, systematic tax on exactly the downstream tasks you're
  measuring.
- **The 20-epoch "diverse masking" benefit is largely wasted.** RoBERTa's dynamic
  masking gain is real but small (~0.5 GLUE points); it is not a substitute for
  the 80/10/10 term, which BERT, RoBERTa, DeBERTa, and ModernBERT all keep.

Fix (`scripts/utils.py`) — matches the docstring:

```python
def mlm_masking(input_ids, mask_token_id, mask_prob=0.15, pad_token_id=0,
                ignore_index=-100, vocab_size=None):
    candidates = (input_ids != pad_token_id) & (input_ids != mask_token_id)
    special = (input_ids == 0) | (input_ids == 101) | (input_ids == 102)  # PAD CLS SEP
    mask = (torch.rand_like(input_ids, dtype=torch.float32) < mask_prob) & candidates & ~special

    labels = torch.full_like(input_ids, ignore_index)
    labels[mask] = input_ids[mask]

    masked_input = input_ids.clone()
    r = torch.rand_like(input_ids, dtype=torch.float32)
    masked_input[mask & (r < 0.80)] = mask_token_id
    if vocab_size:
        rand_tok = torch.randint_like(input_ids, 0, vocab_size)
        mid = mask & (r >= 0.80) & (r < 0.90)
        masked_input[mid] = rand_tok[mid]
    # r >= 0.90 -> leave unchanged
    return masked_input, labels
```

Pass `vocab_size=len(tokenizer)` from `train.py`. Note the added `~special`
guard: as written today, `[CLS]`/`[SEP]` are mask-eligible, so ~30% of your
`[CLS]` positions are being asked to predict `[CLS]` — free loss that looks like
learning.

### 2. The pretraining "test set" is a random 20% of the same corpus, and it is the only thing selecting your model

`notebooks/testing.ipynb` is the only place the corpus is split:

```python
tokenized_datasets = Dataset.from_dict(tokenize_and_prepare_mlm(merged_dataset)).train_test_split(test_size=0.2)
```

That is a random row split of contiguous 512-token chunks cut from the same
documents. Adjacent chunks share authors, dialects, and near-verbatim repeated
passages (Open Greek is heavily duplicated — Perseus texts appear in multiple
editions/corpora). So `Loss/validation` is optimistic and, worse, **it is the
signal you use to pick which checkpoint to export** (`convert_to_hf.py` takes
`final_model.pt`, but the epoch checkpoints you eyeball are ranked against a
contaminated set).

This is the single biggest measurement problem in the repo: **you cannot tell
how good your model is.** Every "we didn't beat aristoBERTo by much" statement is
currently unfalsifiable, because the comparison is running on 2 target words with
n≈108 and n≈125.

Concrete fix — hold out by **document**, not by row, and hold out a
**genre/dialect** split:

```python
# before chunking: group by CTS urn / document id, split on groups
from sklearn.model_selection import GroupShuffleSplit
# or, cheaper and better for this corpus:
#   hold out ALL of tlg0011 (Sophocles), tlg0003 (Plato Apology), ...
```

You already have exactly the right held-out sets sitting in the repo and are not
using them for pretraining selection: **PROIEL** (`spacy_code/assets/
grc_proiel-ud-{train,dev,test}.conllu`) and **Morpheus**
(`lemma-pos/morpheus_*_eval.json`). Report MLM loss/PPL on a genre-disjoint
holdout and pick checkpoints on it.

Also: the `wikidata` split (`data/nlpaueb_tokenized_open_greek_dataset/wikidata`)
is **Modern Greek**. If Modern Greek Wikipedia is in the training mix, that is a
domain-shift dilution of an Ancient Greek model — worth quantifying how many
tokens of the 704M it is, and worth an ablation without it.

### 3. You are continuing from aristoBERTo's *exact* vocabulary and tokenizer, at 6e-4, for 20 epochs

`configs/train.yaml`: `pretrained_model: nlpaueb/bert-base-greek-uncased-v1` —
which is aristoBERTo (`models/external-aristoBERTo/config.json` confirms
`_name_or_path`). So the honest framing of this experiment is *"continue
pretraining aristoBERTo on a different corpus"*, not *"train a new Ancient Greek
BERT"*. And you're comparing it against... aristoBERTo. The ceiling on how much
better that can get is structurally low, because:

- **Same 35k WordPiece vocab, same uncased+cased-ambiguous setup.** You cannot
  beat the baseline by more than the corpus/objective delta allows, because the
  tokenizer — the dominant factor for a morphologically rich, heavily
  diacriticized language — is identical. Your own `morpheus_*_eval.json` shows
  the ceiling effect: your model vs. aristo on Sophocles is **0.896 vs 0.874**
  lemma accuracy. That's +2.2 points, which is what a continued-pretraining-only
  change buys.
- **`tokenizers/modernbert-greek-tokenizer` exists (50,368-token BPE) and is
  never used.** It's wired only to the `pretrained_model: null` from-scratch
  branch, which `train.py` can't even run correctly (it builds a ModernBERT-base
  config, then `convert_to_hf.py` writes it out under a BERT `BertForMaskedLM`
  architecture — see item 9). The `modernbert_tokenized_open_greek_dataset`
  (2.7B tokens, 41 GB) also exists and is unused by `configs/train.yaml`.
  **You have already paid the cost of the better-tokenizer experiment and never
  ran it.**

For Ancient Greek specifically, a cased, diacritic-preserving tokenizer is the
single highest-leverage change available. Uncasing merges accented forms and
destroys information the morphologizer and lemmatizer need — and your spaCy
`morph_per_feat` shows **Gender at f=0.941, the worst feature by a mile**, which
is exactly what accent-loss would predict (ή/οι, α/ας gender/number cues).

Recommendation: run the 50k cased BPE as a real second arm. If from-scratch at
704M tokens is too expensive, distill/re-init embeddings via contextual
initialization rather than another 20-epoch continuation of the same vocab.

### 4. Effective batch size is 128 with LR 6e-4 — the RoBERTa pairing is broken

From `scripts/GreekBERT.3789419.pax184.out`:

```
Total training steps: 214780
Steps per epoch:      10739
Effective batch size: 128
```

`batch_size: 16` × 8 GPUs × `gradient_accumulation_steps: 1` = **128 sequences**
= 65k tokens/step. RoBERTa's 6e-4 was tuned for an **8k-sequence** batch — 64×
larger. 6e-4 at batch 128 is very hot for continued pretraining of an already
converged model; it is a plausible cause of the slow, still-descending loss
curve (epoch 20 val loss 1.98 and *still dropping* — see item 5).

Also note `lr: 6e-4` **and** `max_lr: 6e-4`. `OneCycleLR` uses `max_lr` and
divides by `world_size` internally per param group in some configurations;
either way, having both set to the same value means the `lr` knob is dead and
`docs/archive/ROBERTA_COMPARISON.md` describing "base LR scaled by warmup" is
misleading.

Fix: `gradient_accumulation_steps: 16` → effective batch 2048, keep 6e-4; or keep
batch 128 and drop to ~1e-4–2e-4. Given you're continuing a pretrained model, the
latter is safer and cheaper. Also add `scale_parameter`/`warmup_init` sanity:
print the actual LR at step 100/1000 from the scheduler, not the config value.

## TIER 1 — Real bugs that are cheap to fix

### 5. Training stopped before convergence, and nothing selects the best checkpoint

Epoch 20 val loss **1.9803** and monotonically decreasing through the last epoch
(2.0243 → 2.0064 → 1.9884 → 1.9826 → 1.9803). You are not near a plateau.
`final_model.pt` is saved unconditionally at the end; there is no
`best-by-val-loss` checkpoint, no early stopping. Meanwhile `checkpoint_epoch_*.pt`
saves every 5 epochs — and `convert_to_hf.py::resolve_checkpoint` prefers
`final_model.pt` if present, so **the "best epoch" logic doesn't exist at all.**

Fix: track val loss, save `best_model.pt`, and export from it. Then train longer,
or on more tokens, at a lower LR.

### 6. Validation only runs on rank 0 — your val loss is 1/8 of the test set

`train.py`: the val loop iterates `valid_dataloader`, which uses a
`DistributedSampler(shuffle=False)`. That shards the test set 8 ways. But
`is_main_process` guards only the *printing*; every rank does run the loop, so
each rank scores **its own 1/8 shard** and only rank 0's shard is logged. Not
wrong as a number, but it's 1/8 of the data, and the `epoch_loss`/`avg_val_loss`
are never all-reduced. Add `dist.all_reduce` on `(loss_sum, n_batches)` so the
logged number is the real epoch-average, or restrict the loop to rank 0 with a
non-distributed loader.

### 7. WSD: the shared encoder is trained twice, and the second overwrite decides the reported number

`wsd.py`: `har_classifier` and `kos_classifier` both wrap the **same `model`
object** (`WSDClassifier(bert_model=model, ...)`). Training `harmonia` updates
the encoder in place; then `kosmos` continues from that harmonia-polluted
encoder. The two results are not independent, and the reported number depends on
which word happens to be trained first. Fix: `copy.deepcopy(model)` per target
word.

Same file, `WSDDataset.__getitem__`: `padding='max_length'` with `max_length=512`
on glaux sentences that are mostly short. Every WSD batch is ~95% padding — this
is why WSD is slow, and it's a real accuracy risk too since `target_position` is
taken from `word_ids.index()` on an **unpadded** encoding while the model consumes
the padded one. It happens to line up (padding is right-sided), but it's fragile
and it silently breaks the moment you switch to `padding=True`. Use
`padding=True` with a `collate_fn`, and verify `target_position` against the
*post-padding* encoding.

Also: `AutoModel.from_pretrained` + no `gradient_checkpointing`, no AMP, 10
epochs, `lr=2e-5`, `warmup_steps=100` on ~108 training examples with a 512-token
sequence. Your harmonia curve (best 0.861, final **0.796**) is textbook
overfitting. Fix: `load_best_model_at_end`, and report **mean ± std over ≥5
seeds** — with n=108, the 0.861 vs 0.815 "win" is ~1.5σ and is not a result.

### 8. WSD target-word matching is by surface form, uncased

`target_word='ἁρμονιά'` matched via `sentense['word_ids'].index(word_id)` and
`df` sense lists. But the model is **uncased** and the tokenizer normalizes.
Confirm the target token actually survives tokenization as a distinct position
for every inflected form — otherwise you're reading the hidden state of a
subword or an `[UNK]` (your corpus is **1.26% `[UNK]`**, which is high). A cheap
diagnostic: log how often the target word tokenizes to exactly one token.

### 9. `convert_to_hf.py` rebuilds from config and can silently produce a garbage model

```python
config = AutoConfig.from_pretrained(hp_config.pretrained_model)
model  = AutoModelForMaskedLM.from_config(config)
model.load_state_dict(state_dict)
```

`load_state_dict` without `strict=False` will hard-fail on a shape mismatch —
good — but in the from-scratch branch it builds a **ModernBERT-base** config and
then saves it through a BERT `AutoModelForMaskedLM`, and `config.vocab_size` is
mutated *after* the model is constructed, so the 50,368-token Greek tokenizer
would never match the 50,257-token ModernBERT head. That path is broken. Also
`tokenizer.eos_token = tokenizer.pad_token` is applied to the *training*
tokenizer and then re-saved — harmless here, but the `models/current` export
shows `eos_token: "[PAD]"` baked in, which will silently misbehave in any
generation-style consumer.

Add an assertion: `assert model.config.vocab_size == len(tokenizer)`.

### 10. Dead/duplicated config surface

- `configs/train.yaml` `output_dir: "../models/ManualExport"` vs `TrainingConfig.output_dir` default `"./hf_format"` vs `env.sh` `HF_EXPORT_DIR` — three sources; the env one wins, so the YAML value is decoration.
- `mask_prob` appears in YAML, dataclass default, and the `mlm_masking` default (0.15) — three different values.
- Old logs show `OSError: Repo id must be in the form...: '/cluster/tufts/tuftsai/pnadel01/greek-bert/hf_format'` and the `np.float_` cupy crash — the paths/env work in the README is real and already fixed. Good. But `spacy_code/configs/gpu_base_config.cfg` still hardcodes `/cluster/tufts/tuftsai/pnadel01/greek_bert/hf_format` (note: `greek_bert`, an old path). Delete or repoint it.

## TIER 2 — Evaluation design (this is where "not as much as I expected" actually lives)

### 11. Your benchmarks are too small and too easy to resolve the question you're asking

| Benchmark | Size | Headroom | Status |
|---|---|---|---|
| WSD harmonia | ~108 train / 27 val | — | 0.861 vs 0.815, 1 seed, n=27 val |
| WSD kosmos | ~125 train / 31 val | — | 0.880 vs 0.887 — **you lose** |
| spaCy PROIEL | tag 0.9846 / pos 0.9837 / morph 0.9416 | ~1.5 pts | saturated |
| SBERT retrieval | 96.3% / 95.7% | ~4 pts | near-saturated, and it measures the *translation corpus*, not the language model |

Two of four benchmarks are at >94% and one is n=27. **The expected gain is
smaller than you think because the benchmarks can't express a larger gain.**
This is a measurement ceiling, not a model ceiling.

What I'd add, in priority order:

1. **Per-sentence MLM accuracy / PPL on a genre-disjoint holdout**, sliced by
   century and dialect (Homeric vs Attic prose vs Koine/medical). This is the
   only metric with real headroom, it's cheap, and it's the metric pretraining
   actually optimizes.
2. **Morpheus** as a *proper* held-out lemma benchmark — you already have the
   harness (`lemma-pos/morpheus-eval.py`) and per-author caches. Currently
   `n_tokens: 500`, `seed: 42`. Run the full set, all authors, and report
   coverage-matched accuracy (Morpheus `coverage: 0.728` means 27% of tokens are
   silently skipped — compare only on the intersection, or the number is not
   comparable across models).
3. **POS/lemma on PERSEUS or PROIEL *test* split with a fixed, shared
   fine-tuning recipe** — i.e. freeze the encoder comparison by training the
   identical head for both models, same seeds, 5 seeds each.
4. **A diacritics/orthographic recovery probe** — if you keep the uncased vocab,
   measure the damage directly (masked accent restoration accuracy). It converts
   item 3 from a hypothesis into a number.

### 12. No seed control, no fixed eval protocol, no results table in version control

Results live in `docs/archive/`, loose `.json` files, and notebook outputs.
`runs/` is empty; checkpoints are in `scripts/checkpoints/` with names like
`final_model120.pt`. There is no single table saying "model X, config hash, seed
Y → metric Z". Until that exists, none of the comparisons in this repo are
reproducible, including the baseline comparison that motivated the work.

Suggest: `results/table.md` + a `runs/<RUN_NAME>/metrics.json` written by each
stage, with the git SHA and config hash recorded.

## Tier 3 — Efficiency (frees compute for items 3 and 11)

- **`batch_size: 16` at seq_len 512 on an H200 (141 GB) is leaving most of the GPU
  idle.** A BERT-base MLM at 512 fits 128–256/GPU with bf16. You're paying ~8× the
  wall-clock you need to.
- **FP32 AMP.** `torch.cuda.amp.autocast()` with no `dtype=` defaults to **fp16**,
  and you're running a `GradScaler`. Switch to `torch.amp.autocast('cuda',
  dtype=torch.bfloat16)` and drop the scaler — H200/H100 bf16 needs no loss
  scaling, is more stable at high LR (relevant given item 4), and is faster.
- **`padding='max_length'` in WSD** (item 7) — ~95% wasted FLOPs.
- **`num_workers=4`** with 64 CPUs allocated (`SBATCH_CPUS=64`) — the dataloader is
  almost certainly the bottleneck at batch 16. Raise to 8–16 per process, add
  `persistent_workers=True`, `prefetch_factor=4`.
- **No `torch.compile`, no FlashAttention/SDPA config, no
  `gradient_checkpointing`.** On 8×H200 with SDPA enabled you should be far past
  the throughput implied by these logs.
- **spaCy `discard_oversize = true`** with `batch_by_padded size=2000` silently
  drops long sentences from *training*. Check how many PROIEL sentences that
  removes — if it's non-trivial you're training the parser on an easy subset and
  evaluating on the full test set.

## Bottom line

The gains are small because **(a)** the model is a continuation of the baseline
using the baseline's own tokenizer, so the ceiling is low by construction; **(b)**
the masking implementation lost the 80/10/10 split while running at a 30% mask
rate, which systematically penalizes every unmasked-text downstream task; and
**(c)** the eval suite is saturated, tiny, single-seeded, and selected against a
contaminated random split — so a real gain would likely not be visible even if it
were there.

Fix (c) first. Right now you cannot distinguish "the model is only 2 points
better" from "we can't measure the difference."
